01

Why containers exist

The problem Docker was built to solve, and what a container actually is underneath.

Software fails in a very ordinary way: it works on the machine where it was written and breaks on the machine where it runs. The cause is almost never the code. It is the environment — a different OpenSSL version, a missing shared library, Python 3.9 instead of 3.11, a config file at a path nobody documented.

The traditional fix was to ship the whole machine: a virtual machine image containing the app, its libraries and an entire guest operating system. That works, but a guest OS costs gigabytes of disk, hundreds of megabytes of RAM and tens of seconds to boot. Running forty services means booting forty operating systems.

A container takes a different route. It ships the application and its libraries, and then borrows the kernel of the machine it lands on. There is no guest OS to boot, so a container starts in the time it takes to start a process — because it is a process.

Definition — container

A container is one or more normal Linux processes running on the host kernel, started from a packaged filesystem (an image), with the kernel lying to them about what they can see. Namespaces restrict visibility — which processes, network interfaces, mount points and users exist. Cgroups restrict consumption — how much CPU, memory and I/O they may use. Nothing is emulated and nothing is virtualised.

What the kernel actually does for you

When you run a container, the runtime asks the kernel for a process that cannot see the rest of the machine. Two independent mechanisms do the work.

The vocabulary you need before chapter two

Image
A read-only, layered filesystem plus metadata (default command, environment, exposed ports). It is a template — inert, like an ISO file. Images are built once and reused everywhere.
Container
A running (or stopped) instance of an image, with a thin writable layer on top. One image, many containers.
Registry
A server that stores and serves images. Docker Hub is the public default; most companies also run a private one such as Harbor, ECR, GAR or Artifactory.
Docker daemon
dockerd — the background service that actually builds images and runs containers. It runs as root by default.
Docker CLI
The docker command you type. It is only a client; it sends REST calls to the daemon over a Unix socket at /var/run/docker.sock.
OCI
The Open Container Initiative — the vendor-neutral specs for image format and runtime. It is why an image built by Docker runs under Podman, containerd or Kubernetes without modification.

Real-world use

Why a payments team moved forty services into containers

A mid-sized payments company ran forty Java and Node services on twelve VMs. Each release required a change ticket describing which JDK patch level and which system packages had to be present, and roughly one release in six failed because a host had drifted. Deployments took an hour.

Containerising did not make the code better. What it changed is that the JDK version became part of the build artifact instead of part of the server. The artifact that passed testing is byte-for-byte the artifact that reaches production, verified by digest. Host drift stopped being a category of incident, and the deploy window went from an hour to about four minutes. That is the honest business case for Docker: the environment becomes a versioned artifact rather than an accumulated state.

Know the trade-off

Because containers share the host kernel, a kernel vulnerability can be a full host compromise. For genuinely untrusted or multi-tenant workloads, teams add a second boundary — one VM per tenant, or a sandboxed runtime like gVisor or Kata Containers. "Containers are not a security boundary" is an overstatement, but "containers are a weaker boundary than VMs" is simply true. Chapter 11 covers what to do about it.

02

Installing the engine

Getting a working daemon on Ubuntu/Debian or RHEL/Rocky, and the one post-install decision that matters.

Install Docker from Docker's own repository, not from the distribution's. Distro packages lag by months and, on RHEL derivatives, may not exist at all. Pick your platform — every command on this page updates.

Install Ubuntu / Debian



  


  
Start the daemon and prove it works

  


  
If hello-world prints its greeting, four things just worked: the CLI reached the daemon over the socket, the daemon authenticated to Docker Hub, it pulled and unpacked an image, and it ran a container to completion. That is the whole system in one command.


  
The docker group decision

  
By default only root can talk to /var/run/docker.sock. Adding yourself to the docker group removes the need for sudo:

  
sudo usermod -aG docker $USER
newgrp docker        # or log out and back in


  

    Understand what you just granted
    
Membership of the docker group is equivalent to passwordless root. Anyone in it can run docker run -v /:/host -it alpine chroot /host sh and own the machine. On shared or production hosts, either keep sudo docker, or install rootless mode, which runs the daemon as an unprivileged user inside a user namespace:

    
dockerd-rootless-setuptool.sh install
export DOCKER_HOST=unix:///run/user/$UID/docker.sock

    
Rootless mode costs you a few features — binding ports below 1024 without extra setup, some network drivers, certain cgroup controls — and is worth it on anything shared.

  


  
Where things live afterwards

  

    
/var/lib/docker
Images, container writable layers, volumes and build cache. This directory grows without limit until you prune. Give it its own filesystem on a real server.

    
/etc/docker/daemon.json
Daemon configuration: log driver and rotation, registry mirrors, default address pools, storage driver. Changing it needs a daemon restart.

    
/var/run/docker.sock
The API socket. Mounting this into a container hands that container control of the host — treat it as a credential.

    
Firewall interaction

  


  

    The classic first surprise
    
Publishing a port with -p 5432:5432 writes an iptables DNAT rule that is evaluated before your ufw or firewalld rules. A database you thought was firewalled off is reachable from the internet. Bind it to loopback instead — -p 127.0.0.1:5432:5432 — and you will save yourself an incident.

  


  

    Real-world use
    
Why the install method ends up in the runbook

    
On a fleet, nobody types these commands — they go into Ansible or cloud-init, pinned to a specific docker-ce version. Teams pin because a minor engine upgrade has, historically, changed default behaviours such as the cgroup driver or the default logging driver, and a rolling upgrade that changes both at once is hard to debug at 2 a.m. The rule most teams settle on: pin the engine version, upgrade it deliberately on one canary node, and keep /var/lib/docker on a separate volume so a full disk takes out containers rather than the whole host.

The container lifecycle

      
Created, running, paused, exited, gone — and which commands move between them.

    

  

  


  
Most early confusion with Docker comes from treating a container like a small server. It is not. A container is a wrapper around one foreground process. When that process exits, the container exits — immediately, whatever else it was doing. Learning the state machine below removes about half of the questions a new engineer asks in their first month.

    The most common beginner bug
    
A container that exits instantly with code 0 is usually correct behaviour, not a failure. docker run ubuntu starts bash, bash has no terminal attached, bash exits, the container exits. Containers need a process that stays in the foreground: nginx -g "daemon off;", not systemctl start nginx. Never try to run an init system or a daemoniser inside a container unless you know exactly why.

  


  

    Real-world use
    
Restart policies as the poor engineer's orchestrator

    
On a single VM without Kubernetes, --restart unless-stopped plus a healthcheck is a genuinely reasonable production setup for internal tools. It survives host reboots and process crashes. What it does not do is move a workload when the host dies, which is the line where teams graduate to an orchestrator. Plenty of small companies never cross it, and that is a legitimate choice rather than a failure of ambition.

  

  







  

    04
    

      
Images, layers and copy-on-write

      
Why a 900 MB image only costs 40 MB on the second host, and where your writes actually go.

    

  

  


  
An image is not a single file. It is a stack of layers, each layer a tarball of filesystem changes produced by one build instruction. Layers are content-addressed: their identity is the SHA-256 of their contents, so two images that share a base share those bytes on disk and on the wire.


  
When a container starts, the runtime stacks the image's read-only layers with a union filesystem (overlay2 on modern Linux) and adds one thin writable layer on top. Reads fall through the stack to the first layer that has the file. Writes go to the top.


  

  
Consequences you will meet in week one

  

    
Layers are additive
Deleting a file in a later layer does not shrink the image — it only writes a whiteout marker. A secret added in layer 3 and deleted in layer 6 is still extractable from the image. Never let a credential touch any layer.

    
Writes are slower
The first write to a large file from a lower layer copies the whole file upward. Databases must use a volume, not the writable layer.

    
Layer count matters, a bit
Each RUN, COPY and ADD makes a layer. Chaining related commands with && keeps the count sane, though overlay2 handles many layers fine — clarity usually beats micro-optimisation.

    
Tags are pointers
nginx:1.27 can be repointed at new bytes tomorrow. Only nginx@sha256:… is immutable. Chapter 7 goes into this.

  


  
Reading an image's history

  
$ docker history acme/api:1.4 --format "table {{.Size}}\t{{.CreatedBy}}"
SIZE      CREATED BY
2.1MB     COPY app/ /app/  # buildkit
88.4MB    RUN pip install -r requirements.txt
0B        COPY requirements.txt /app/
41.2MB    RUN apt-get install -y python3
74.8MB    /bin/sh -c #(nop) ADD file:8f0d… in /

  
Read it bottom-up: that is build order. The 88 MB pip layer is the one to attack — and the fact that it sits above the tiny COPY app/ layer in build order is exactly what makes the cache work well here. Chapter 5 explains why.


  

    Real-world use
    
Standardising base images across a company

    
Platform teams commonly publish a small set of blessed base images — company/python:3.12, company/java:21 — patched weekly and scanned in CI. Every service builds FROM one of them. Two things follow. Patching a CVE in OpenSSL becomes one base rebuild plus a fleet rebuild rather than sixty separate investigations. And because every service shares those bottom layers, a node that already runs one service pulls the next one in seconds. The cost is governance: someone has to own the base images and actually rebuild them, or you get the illusion of central control with none of the patching.

  

  







  

    05
    

      
Dockerfiles and the build cache

      
Writing the recipe, and ordering it so your builds take seconds instead of minutes.

    

  

  


  
A Dockerfile is a sequential recipe. Each instruction runs against the result of the previous one and produces a new layer. docker build sends the build context — the directory you point it at — to the daemon, then executes the recipe.


  

    
InstructionMeaningNotes for beginners

    
      
FROMBase image to start fromAlways first (after optional ARG). Pin a real tag.

      
WORKDIRSet and create the working directoryUse it instead of RUN cd — each RUN is a new shell.

      
COPYCopy from build context into the imagePrefer over ADD. ADD also untars and fetches URLs, which surprises people.

      
RUNExecute a command at build timeCreates a layer. Clean package caches in the same RUN or the cleanup does nothing.

      
ENVEnvironment variable, build and runtimeVisible in docker inspect. Not for secrets.

      
EXPOSEDocument a portDocumentation only — it publishes nothing. -p does that.

      
USERSwitch the UID for later instructions and runtimePut it as late as possible, and always use it.

      
ENTRYPOINTThe fixed executableExec form ["nginx"], not shell form, so signals reach PID 1.

      
CMDDefault arguments, overridable on the command lineWith ENTRYPOINT, CMD supplies default args.

      
HEALTHCHECKHow to tell if the app is aliveCovered in chapter 12.

    
  


  
The build context and .dockerignore

  
docker build . tars the entire directory and uploads it to the daemon before anything runs. If .git, node_modules and a 4 GB test fixture directory are in there, you pay for all of it on every build — and a careless COPY . . bakes them into the image.

  
# .dockerignore — write this before your first build, not after
.git
node_modules
*.log
.env
dist
**/__pycache__
Dockerfile
docker-compose.yml


  
How the cache decides

  
For each instruction, BuildKit computes a key from the instruction text plus, for COPY and ADD, a checksum of the files being copied. If the key matches a previous build, the layer is reused. The first miss invalidates every layer below it — cache invalidation cascades downward and never recovers.

  
That single rule dictates Dockerfile structure: put what changes rarely at the top, what changes on every commit at the bottom.

The optimised Dockerfile, annotated

  
FROM node:20-slim
WORKDIR /app

# Dependency manifests only. These change rarely,
# so the expensive npm ci below stays cached across commits.
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

# Application source last: it changes every commit,
# and only the two cheap layers below it are rebuilt.
COPY src/ ./src/

USER node
EXPOSE 3000
CMD ["node", "src/index.js"]


  

    Cleanup must share a RUN
    
This does nothing for image size, because the delete happens in a new layer that cannot shrink the one below it:

    
RUN apt-get update && apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*        # too late

    
This works, because everything happens inside one layer:

    
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl \
 && rm -rf /var/lib/apt/lists/*

  


  

    Real-world use
    
A nine-minute CI build, fixed by moving two lines

    
A team's pipeline took roughly nine minutes per commit, of which seven were npm ci. Their Dockerfile began with COPY . ., so every commit — including README edits — invalidated the dependency install. Splitting the copy into manifests-first and source-last brought typical builds to about forty seconds, with the seven-minute path taken only when package-lock.json genuinely changed. Nothing else was altered. On a team merging thirty times a day, that is roughly four engineer-hours of waiting recovered daily, and it is the single highest-value Dockerfile change most teams can make.

  

  







  

    06
    

      
Multi-stage builds

      
Compile in a big image, ship a small one, and leave the toolchain behind.

    

  

  


  
Building software needs compilers, headers, package managers and dev dependencies. Running it usually needs none of them. A single-stage build ships all of it anyway — a Go binary of 6 MB arriving inside a 900 MB image that contains the Go toolchain.

  
A multi-stage build uses several FROM statements. Earlier stages do the work; the final stage starts from a minimal base and copies in only the finished artifact. Everything else is discarded and never reaches a registry or a host.


  

  
# ---- stage 1: build ----
FROM golang:1.22 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/server ./cmd/server

# ---- stage 2: run ----
FROM gcr.io/distroless/static:nonroot
COPY --from=build /out/server /server
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/server"]

    Debugging a distroless container
    
There is no shell to exec into, but you can attach one from outside: docker run -it --pid container:api --network container:api nicolaka/netshoot joins the target's namespaces from a fully equipped image. Modern Docker also offers docker debug. The debugging tools live in a separate image rather than in your production one — which is the correct place for them.

  


  

    Real-world use
    
Image size is a deployment-speed and compliance number

    
A 900 MB image pulled onto 200 nodes moves roughly 180 GB across the network on a cold rollout, and autoscaling that has to pull before it can serve traffic responds in minutes rather than seconds. The same reduction shows up in the vulnerability report: a distroless image has no bash, no apt and no OpenSSH, so the weekly scan lists a handful of CVEs instead of two hundred — and the ones it does list are actually in your code. Teams that report "we cut our CVE count by 90%" have usually not fixed 90% of anything; they deleted the packages they were never using.

  

  







  

    07
    

      
Registries, tags and digests

      
How images move between machines, and why :latest causes outages.

    

  

  


  
A registry is an HTTP service that stores layers and manifests. docker pull and docker push speak its API. The full name of an image is longer than it usually looks:


  
registry.example.com:5000/platform/api:1.4.2
└──────────┬──────────┘ └───┬───┘ └┬┘ └─┬─┘
        registry        namespace  name  tag

# When you omit the registry, Docker silently assumes Docker Hub:
docker pull nginx        # → docker.io/library/nginx:latest


  
Tags are mutable. Digests are not.

  
A tag is a human-friendly pointer that the registry lets anyone with push rights move. nginx:1.27 today and nginx:1.27 next month can be different bytes. A digest is the SHA-256 of the image manifest — it identifies one exact image forever.


  
$ docker pull nginx:1.27
$ docker inspect nginx:1.27 --format '{{index .RepoDigests 0}}'
nginx@sha256:9f2a5d1c…4c17

# Deploy by digest when it must be reproducible:
docker run nginx@sha256:9f2a5d1c…4c17


  

    Why :latest hurts
    
Three nodes pull app:latest on Monday, a fourth scales up on Thursday after someone pushed a new build. You now run two different versions behind one load balancer, and nothing in your deployment history records that. :latest is not even "the newest" — it is simply the tag applied when you do not specify one. Use immutable version tags for humans and digests for machines.

  


  
A tagging scheme that works

  

    
TagMoves?Used by

    
      
api:1.4.2NeverDeployments, rollbacks, incident reports

      
api:1.4On each patchHumans wanting the newest patch of a minor line

      
api:git-9f2a5d1NeverTracing a running container back to a commit

      
api:mainEvery mergeStaging environments only

      
api@sha256:…Never, by constructionProduction manifests and anything auditable

    
  


  
# Log in, tag the local build, push
docker login registry.example.com
docker tag acme/api:1.4.2 registry.example.com/platform/api:1.4.2
docker push registry.example.com/platform/api:1.4.2

# Credentials land in ~/.docker/config.json — base64, NOT encrypted.
# On servers use a credential helper or a short-lived registry token.


  

    Real-world use
    
The pull-through cache that pays for itself

    
Public registries rate-limit anonymous pulls. A CI fleet doing hundreds of builds an hour hits those limits, and builds start failing for reasons that have nothing to do with the code. The standard fix is a pull-through cache — a private registry configured as a mirror — so the first pull of node:20-slim crosses the internet and the next thousand come off the LAN. It removes a class of flaky pipeline failure, cuts build time, and gives you a record of exactly which external images your organisation depends on. That last one matters more than teams expect the first time a supply-chain advisory lands.

  

  







  

    08
    

      
Volumes and bind mounts

      
Containers are disposable. Your data must not be.

    

  

  


  
Everything a container writes outside a mount goes to its writable layer, and docker rm deletes that layer. This is by design — it is what makes containers replaceable — but it means persistence has to be explicit. There are three options and they behave very differently.


  

    
Writable layer
The default. Fast to set up, deleted with the container, invisible to other containers, and slow for heavy writes because of copy-on-write. Correct for genuinely temporary files only.

    
Named volume
-v pgdata:/var/lib/postgresql/data. Docker creates and manages a directory under /var/lib/docker/volumes/. Survives container removal, can be backed up, can be shared, and works with volume drivers for NFS or cloud storage. The default choice for production data.

    
Bind mount
-v /home/dev/app:/app. Maps a specific host path in. You control exactly where the bytes are; the container sees host permissions and host UIDs. The default choice for local development and for injecting config files.

Syntax you will see in the wild

  
# Named volume — Docker manages the location
docker run -d -v pgdata:/var/lib/postgresql/data postgres:16

# Bind mount, read-only — the pattern for injecting config
docker run -d -v /etc/myapp/config.yaml:/app/config.yaml:ro acme/api:1.4

# The explicit --mount form. Verbose, but it fails loudly on typos
# instead of silently creating an empty directory, which -v does.
docker run -d \
  --mount type=volume,source=pgdata,target=/var/lib/postgresql/data \
  --mount type=bind,source=/etc/myapp,target=/etc/myapp,readonly \
  postgres:16

# Housekeeping
docker volume ls
docker volume inspect pgdata
docker volume rm pgdata          # fails while a container uses it — good
docker volume prune              # deletes every unused volume. Read the prompt.


  

    Two traps worth memorising
    
The typo trap. -v /ect/myapp:/app/config does not error. Docker creates /ect/myapp as an empty directory and mounts it, and your app starts with no config. --mount would have refused.

    
The UID trap. A bind mount carries host ownership. If the container runs as UID 10001 and the host directory is owned by UID 1000, you get permission denied. Fix it on the host (chown) or match the UID (--user 1000:1000). Do not fix it by running as root.

  


  
Backing up a volume

  
# Mount the volume plus a bind mount for the output, then tar it
docker run --rm \
  -v pgdata:/data:ro \
  -v "$PWD":/backup \
  alpine tar czf /backup/pgdata-$(date +%F).tar.gz -C /data .

  
For a database, stop the container or use the database's own dump tool first — a tar of live data files is a crash-consistent copy, not a clean backup.


  

    Real-world use
    
Bind mounts in development, volumes in production

    
The everyday development pattern is to bind-mount the source tree into the container so a file save is reflected instantly without a rebuild — edit on the host with your normal editor, run in the container with production's exact runtime. In production that same bind mount would be a liability: it ties the container to a host path, breaks when the workload is rescheduled elsewhere, and quietly grants write access to a host directory. Production uses named volumes with a driver that points at real storage, so a replaced container reattaches to the same data and a dead host does not take the data with it.

  

  







  

    09
    

      
Networking and publishing ports

      
Why your container is unreachable, and why one container cannot find another by name.

    

  

  


  
Every container gets its own network namespace: its own interfaces, routing table and firewall rules. By default it is attached to a bridge network, which behaves like a virtual switch inside the host. Two facts explain almost every networking problem a beginner hits.


  

    
1. Container ports are private until published. A process listening on port 80 inside a container is reachable from other containers on the same network, and from nowhere else. -p 8080:80 writes an iptables DNAT rule that forwards host port 8080 to it.

    
2. The default bridge has no DNS. On bridge, container names do not resolve. On a user-defined network they do, automatically. This is why the first instruction in every good tutorial is "create a network".

# Inside web, the connection string is simply the service name:
#   postgres://user:pass@db:5432/app

docker network ls
docker network inspect appnet          # see attached containers and their IPs
docker network connect appnet legacy-a # attach a running container to a second network

User-defined bridgeSame, plus DNS by container name and better isolationAlmost everything on a single host

    Real-world use
    
Network segmentation as a cheap blast-radius control

    
A common production layout puts the reverse proxy and the app on a frontend network, and the app and the database on a backend network. The app is attached to both; the proxy has no route to the database at all. If the proxy is compromised, there is no path to the data — not a firewall rule that might be misconfigured, but a missing route. This costs one extra docker network create and is one of the highest value-per-effort things in the whole toolkit.

  

  







  

    10
    

      
Docker Compose

      
One file that describes the whole stack, so nobody has to remember nine docker run commands.

    

  

  


  
By chapter nine you can run a stack by hand: create a network, start the database with a volume, start the app with the right environment, publish a port. Compose puts that in a YAML file which lives in the repository, gets reviewed, and can be run identically by every engineer.


  
# compose.yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./secrets/db_password:/run/secrets/db_password:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 10
    networks: [backend]

  cache:
    image: redis:7-alpine
    networks: [backend]

  api:
    build: .
    depends_on:
      db:      { condition: service_healthy }
      cache:   { condition: service_started }
    environment:
      DATABASE_URL: postgres://postgres@db:5432/app
      REDIS_URL: redis://cache:6379
    networks: [backend, frontend]

  proxy:
    image: nginx:1.27
    depends_on: [api]
    ports:
      - "127.0.0.1:8080:80"
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
    networks: [frontend]

volumes:
  pgdata:

networks:
  frontend:
  backend:


  
Compose creates the networks and volumes, builds what needs building, and starts services in dependency order. Note that proxy is not on backend — it has no route to the database, exactly as described in chapter 9.

    depends_on is weaker than it looks
    
Plain depends_on: [db] waits for the container to start, not for Postgres to accept connections. Your API will happily start and immediately fail to connect. Either use condition: service_healthy with a real healthcheck as above, or — better — make the application retry its database connection on startup. Applications that survive a database restart are more valuable than orchestration that pretends restarts never happen.

  


  

    
CommandWhat it does

docker compose up -d --buildForce a rebuild first — the flag people forget after changing a Dockerfile

docker compose up -d --scale api=3Run three replicas of one service behind the proxy

docker compose down -vThe same, plus deletes named volumes. This is how people lose dev databases.

      
docker compose configPrint the fully resolved file after variable substitution — the first debugging step

    
  


  

    Real-world use
    
Onboarding measured in minutes

    
The clearest win from Compose is the first day of a new engineer. Instead of a wiki page listing Postgres 14, Redis, a message broker and four environment variables, the instruction is git clone then docker compose up. Ten minutes later they have a running stack, and the wiki page cannot drift because the file is the environment and it is reviewed like code.

    
The honest limit: Compose runs on one host. It has no rescheduling, no rolling updates and no multi-host networking beyond Swarm. It is excellent for development, CI and modest single-server production, and it is where teams stop until they genuinely need an orchestrator — at which point the same images and roughly the same service definitions carry over to Kubernetes.

Security hardening

      
Seven decisions that separate a default container from a defensible one.

    

  

  


  
A container out of the box runs as root, keeps a broad set of capabilities, has a writable filesystem and takes its secrets from environment variables. None of that is required, and each has a one-flag fix. The lab below scores a configuration and shows the command it produces.

Secrets: the rule and the reason

  
An environment variable is visible in docker inspect, in the daemon's API responses, in /proc/<pid>/environ, in most crash reporters, and in every child process the app spawns. It is a poor place for a password.

  
# Don't
docker run -e DB_PASSWORD=hunter2 acme/api:1.4

# Do — mount it, read it, let the file permissions do the work
docker run \
  --mount type=bind,src=/run/secrets/db_password,dst=/run/secrets/db_password,ro \
  -e DB_PASSWORD_FILE=/run/secrets/db_password \
  acme/api:1.4

# At build time, never bake a secret into a layer. Use a build secret,
# which is mounted for one RUN and never written to the image:
#   RUN --mount=type=secret,id=npmrc npm ci
docker build --secret id=npmrc,src=$HOME/.npmrc -t acme/api:1.4 .


  

    Layers remember
    
A secret copied in and deleted in a later instruction is still present in the earlier layer and can be extracted by anyone who pulls the image. If a credential ever touches a build, treat it as compromised and rotate it. There is no cleanup that fixes this after a push.

  


  
A baseline worth adopting

  

    
Run as non-root
Add a USER in the Dockerfile. If the app must bind port 80, either give it NET_BIND_SERVICE or listen on 8080 and publish it as 80.

    
Drop capabilities
--cap-drop ALL, then add back only what breaks. Most web services need nothing.

    
Read-only root filesystem
--read-only --tmpfs /tmp. Forces you to notice every path the app writes to, which is a useful thing to know.

    
No new privileges
--security-opt no-new-privileges stops setuid binaries from escalating inside the container.

    
Resource limits
--memory, --cpus, --pids-limit. A fork bomb in one container should not take the host down.

    
Never mount docker.sock
Mounting /var/run/docker.sock gives that container full control of the host. If a build agent truly needs it, isolate it on its own machine.

    
Scan and rebuild
docker scout cve acme/api:1.4 or Trivy in CI. Scanning without a rebuild cadence just produces a longer report each week.

  


  

    Real-world use
    
What an audit actually asks for

    
Compliance reviews rarely ask "is Docker secure". They ask three answerable questions: can you prove which image version is running in production (digests and a deployment record), can you show that images are scanned and rebuilt on a schedule (pipeline logs), and can you demonstrate that a compromised container cannot reach the host or the database (non-root, dropped capabilities, network segmentation). Every one of those is a decision made once in a Dockerfile or a pipeline, not a control bolted on later — which is why hardening is much cheaper to do at the start of a containerisation project than eighteen months in.

Operating containers

      
Logs, healthchecks, limits, disk, and a systematic way to debug a container that will not stay up.

    

  

  


  
Logs

  
A containerised app should write to stdout and stderr and nothing else. No log files, no rotation logic, no syslog configuration. The daemon captures both streams; whatever collects logs on the host takes it from there.

  
docker logs -f --tail 100 --timestamps web
docker logs --since 15m web

# Without rotation, /var/lib/docker/containers grows until the disk is full.
# This is one of the most common causes of "the whole host died".
# /etc/docker/daemon.json:
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}


  
Healthchecks

  
A running container is not necessarily a working one. A healthcheck gives the daemon — and Compose, and your orchestrator — a real answer.

  
# In the Dockerfile
HEALTHCHECK --interval=30s --timeout=3s --start-period=20s --retries=3 \
  CMD curl -fsS http://localhost:8080/healthz || exit 1

# Check it
docker inspect web --format '{{.State.Health.Status}}'   # starting | healthy | unhealthy

  
Make the endpoint check what the service needs — a database ping, not just "the process is alive". But keep it cheap: it runs every interval on every replica, and an expensive healthcheck can become its own outage.


  
Limits

  
docker run -d --name api \
  --memory 512m --memory-reservation 256m \
  --cpus 1.5 --pids-limit 200 \
  acme/api:1.4

docker stats --no-stream        # live CPU, memory, network, I/O per container

  
Without --memory, one leaking container can consume all host RAM and the kernel will kill something — quite possibly a different, innocent container. Set limits from the start.


  

    

      Lab 8 · Exit code triage
      Troubleshooter
    

    

      
Goal: a container is not running. Read the exit code from docker ps -a, then know which command to run next.

      

      

    

  


  
A debugging order that works

  
docker ps -a                          # 1. is it running? what exit code?
docker logs --tail 100 web            # 2. what did it say before it died?
docker inspect web                    # 3. mounts, env, network, OOMKilled, restart count
docker exec -it web sh                # 4. if it IS running: look from inside
docker run --rm -it --entrypoint sh acme/api:1.4   # 5. if it isn't: bypass the entrypoint
docker events --since 10m             # 6. what did the daemon do, in order?


  

    Disk is the silent failure
    
Images, stopped containers, unused volumes and build cache accumulate quietly until a build fails with "no space left on device". Check with docker system df, and reclaim with docker system prune -a. Add --volumes only when you are certain — that flag deletes data no container currently references, which on a host with a stopped database container is exactly the data you wanted.

  


  

    Real-world use
    
The runbook a team actually keeps

    
Mature container runbooks are short, and they are mostly about the host rather than the application: log rotation configured in daemon.json, /var/lib/docker on its own filesystem with a disk alert at 75%, memory limits on every service, a weekly docker system prune on build agents, and healthchecks wired into whatever restarts things. Four of those five are decisions made once. The teams that get paged at 3 a.m. for container problems are, in the overwhelming majority of cases, missing log rotation or missing memory limits.
